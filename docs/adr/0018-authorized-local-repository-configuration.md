# ADR-0018: Authorized local repository configuration boundary

- Status: Accepted
- Date: 2026-09-05

## Context and task contract

M1 is complete on protected `main` at `8a030d3`, making M2-S01 the earliest eligible slice. Authenticated remote readback found no open pull request or competing branch, so this task is claimed by `feat/m2-s01-authorized-root-config`.

Traceability: `M2-S01`, `FMU-FR-001`, `FMU-FR-026`, `FMU-NFR-009`, `FMU-NFR-011`, `FMU-NFR-013`, `UC-05`, PROJECT_SPEC Sections 5.1, 10, 12, 13, and 14, ARCHITECTURE Sections 3.3, 5.1, 8.1, and 10, SECURITY_PRIVACY Sections 4, 5 (T-02 through T-04), 7, 8, 10, and 11, and ADR-0001/0002/0003/0005. No `FMU-E-*` behavioral evaluation applies because this slice establishes owner-side source authorization and path/limit configuration; it does not collect evidence, derive a Claim or Demand Profile, compile a DCP, or change consumer behavior.

The observable result is that a bounded JSON configuration resolves to a detached, deeply immutable set of canonical authorized roots and selected repositories only when every selected repository is a canonical directory inside its named root. Invalid shape/version/limits, unavailable paths, duplicate physical identities, and canonical escape return only a typed content-free failure. Resolution may inspect path metadata needed for `realpath` and directory type, but it neither enumerates nor reads repository content.

In scope are one implementation-internal configuration and path-authorization module in the Community Provider, an injected canonical-directory port and its Node metadata-only implementation, deterministic unit tests, temporary-directory integration tests, the security boundary documentation, this ADR, changelog/README/roadmap synchronization, and the M2-S01/M2-S02 state proposal. Hard constraints are no public schema or Provider operation, source-content read, directory enumeration, Git command, repository code execution, network, persistence, owner CLI, Claim/Evidence production, dependency, package publication, release, deployment, private-repository access, or compatibility expansion.

The configuration starts at internal version `0.1.0`; it is neither a public interchange contract nor a persisted Profile Store. A later incompatible or persisted form requires an explicit migration path and cannot be silently accepted. Allowed effects are local code/document edits, synthetic temporary directories, a short-lived branch, the authorized pull request and squash merge, and branch deletion. Stop on a higher-authority conflict, path authorization that cannot fail closed, a need to read repository content, a public-contract/dependency change, ownership conflict, unresolved high-severity finding, or protected CI failure.

Required verification covers exact closed JSON shape and byte limit; identifier, array, string, and collection-budget bounds; absolute root and safe source-relative syntax; platform-aware canonical identity and containment; root/repository physical-identity duplicates; root selection by opaque ID; missing/non-directory/error states; junction or symlink escape where supported; all-or-nothing content-free failure; immutability/non-mutation; metadata-only implementation source; no network/listener/execution primitive; full project checks; clean lockfile install; dependency audit; complete-diff review; and protected pull-request plus post-merge CI.

## Decision

- Keep the boundary implementation-internal to `@fork-me-up/community-provider`. Protocol and Core receive neither filesystem paths nor Community configuration types. The Profile Provider read contract remains unchanged and still accepts no source root or collector instruction.
- Accept UTF-8 JSON capped at 32,768 bytes with the exact closed shape `configVersion`, `authorizedRoots`, `repositories`, and `limits`. Version `0.1.0` is the only accepted version. Unknown fields, accessors, implicit defaults, coercion, and partial recovery are rejected.
- Each authorized root has an opaque `rootId` and an explicitly selected absolute platform path. Each selected repository has an opaque `repositoryId`, names exactly one `rootId`, and uses `.` or a forward-slash source-relative path. Absolute, drive-qualified, backslash, empty-segment, dot-segment, traversal, control-character, and colon-bearing repository paths are rejected before filesystem access.
- Resolve paths through an injected `CanonicalDirectoryPort`. The Node implementation uses only `realpath` and `stat`, requires a directory, and performs no directory enumeration or content read. A selected repository candidate is constructed from the canonical root, recanonicalized, and accepted only when platform-aware relative-path comparison proves it is the root itself or a descendant.
- Canonical identity is case-insensitive on Windows and case-sensitive for the current POSIX policy. Windows device namespaces are rejected; drive-letter and UNC canonical paths remain distinct. Aliased/case-varied roots or repositories resolving to the same physical identity are duplicates. Only opaque IDs, canonical paths, identities, and accepted limits enter the private resolved value; input path text is never reflected in an error.
- Enforce at most 16 roots and 32 selected repositories. A required limits object caps repositories, files per repository, bytes per file, total bytes per repository, tree depth, duration, and concurrency. Configuration may choose lower values but cannot exceed the fixed implementation ceilings. Total-byte allowance cannot be smaller than the per-file allowance.
- Resolution is all-or-nothing and returns one of `invalid-config`, `unsupported-version`, `limit-exceeded`, `path-unavailable`, or `not-authorized`, with only category and retryability. It returns no partial root/repository, path, identifier, native error, or stack. The successful result is detached and deeply immutable.
- Canonicalization at configuration time is a snapshot, not a permanent capability. M2-S02 collectors must recanonicalize every path at the point of use, constrain it to the stored canonical root, and handle replacement races; they may never treat string concatenation or this earlier check as sufficient authorization.

## Consequences and alternatives

Later collectors receive one narrow, testable authority object instead of interpreting arbitrary paths. Relative repository selection makes root intent explicit, while physical canonicalization detects symlink/junction escape and duplicate aliases before content collection. Fixed ceilings make future traversal budgets available before a scanner exists, and content-free errors are safe for normal diagnostics.

The private resolved value contains absolute canonical paths because a local collector must open them; those paths remain inside the owner-side process and are prohibited from DCPs, normal logs, Provider errors, and consumer operations. Filesystem replacement after resolution remains possible, so point-of-use enforcement is deliberately deferred but mandatory. Only Windows is verified in this slice; POSIX behavior is deterministic in injected tests but is not a macOS/Linux compatibility claim.

Accepting arbitrary absolute repository paths is rejected because it obscures which root authorized them. Lexical-only containment is rejected because links and aliases cross physical boundaries. Persisting a source grant, exposing configuration through MCP, placing paths in Protocol/Core, reading a directory to validate it, silently dropping invalid entries, or inferring the developer's repositories are rejected. A new dependency is unnecessary because Node supplies the required path and metadata primitives.

## Validation

Run the pinned Windows Node.js/npm path and `npm run check`. Unit tests use a synthetic path port to cover Windows/POSIX identity, containment, every closed-shape and limit failure, duplicates, immutability, non-mutation, all-or-nothing behavior, and content-free errors. Integration tests use temporary synthetic directories and, where the platform permits, a directory link that points outside the authorized root. Static inspection rejects content-read, enumeration, process-execution, network, and listener primitives in the Node implementation. Review the workspace dependency graph, documentation links, complete diff, and `npm audit --audit-level=high`; then require protected pull-request and post-merge CI before the proposed queue transition becomes authoritative.
