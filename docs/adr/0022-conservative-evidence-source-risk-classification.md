# ADR-0022: Conservative evidence source-risk classification

- Status: Accepted
- Date: 2026-09-05

## Context and task contract

M2-S04 is integrated on protected `main` at `95e10d2`, making M2-S05 the earliest eligible slice. Authenticated readback found successful current-`main` CI, no open pull request, no competing branch/worktree, and a clean tree. This task is claimed by `feat/m2-s05-source-risk-classification`.

Traceability is `M2-S05`, `FMU-FR-005`, `FMU-FR-006`, `FMU-FR-019`, `FMU-NFR-005`, `FMU-NFR-006`, `FMU-NFR-011`, `FMU-E-007`, UC-05/UC-07, PROJECT_SPEC Sections 11 through 15, PROTOCOL Sections 2.1 and 5.1/5.2, ARCHITECTURE Sections 5.1/5.2 and 12, SECURITY_PRIVACY T-01/T-04/T-05 and Sections 8/10/11, ENGINEERING Sections 3 through 8, ADR-0008, ADR-0019, ADR-0020, and ADR-0021. The observable result is that bounded M2 filesystem, Git, and authorship snapshots plus explicit private annotations deterministically produce sanitized per-file source-risk evidence records that expose and down-rank fork, template, generated, vendored, tutorial, duplicated, and uncertain contributions while preserving attribution and source limitations.

In scope are a closed implementation-internal source-risk configuration resolver, a pure snapshot classifier, conservative fixed path indicators, cross-file SHA-256 duplicate detection, bounded Git-path/authorship association, immutable private output, adversarial unit/integration tests, `FMU-E-007`, this ADR, and synchronized protocol/architecture/security/README/changelog/roadmap documentation. Hard non-goals are remote-origin inspection, network or hosting API access, repository execution, raw-content similarity, arbitrary glob/regex configuration, claims that unflagged content is original, capability Evidence or Claim production, confidence aggregation, correction precedence, persistence, owner CLI, Provider/MCP/adapter changes, public schema changes, dependencies, release, or migration.

The configuration and source-risk snapshot begin at implementation-internal version `0.1.0`; no released or persisted data requires migration. Allowed effects are local source/document edits, temporary synthetic repositories, deterministic checks, a short-lived branch, the already authorized pull request/squash merge, and branch deletion. Stop on a higher-authority conflict, raw source/identity/absolute-path output, a risk rule that increases support, uncontrolled pattern execution, a public-contract/dependency change, ownership conflict, unresolved high-severity finding, or protected CI failure.

Required verification covers exact configuration version/shape/byte/count/identifier/path limits; authentic resolved configuration; annotation duplicates and dangling targets; exact filesystem/Git/authorship snapshot validation and cross-snapshot consistency; deterministic ordering and deep immutability; every required risk flag; explicit repository/path annotations; case-normalized fixed path indicators; cross-repository and same-repository digest duplicates; missing or limited authorship; shallow/truncated history; normal versus reduced support; weak/moderate strength ceilings; fixed preserved limitations; no unflagged-original claim; malformed/canary inputs and content-free failures; real M2 collector/assessor integration; offline/pure static inspection; full checks; clean install; audit; Markdown links; complete-diff review; and protected pull-request plus post-merge CI.

## Decision

- Keep source-risk configuration and classification implementation-internal to `@fork-me-up/community-provider`. The output is private pre-Evidence normalization data, not the public Evidence schema, a Claim, a DCP, a profile, or a provider response.
- Resolve at most 32 KiB of exact JSON `0.1.0`. Repository annotations may mark `fork`, `template`, `tutorial`, or `uncertain`; path annotations may mark `template`, `generated`, `vendored`, `tutorial`, or `uncertain`. Require safe opaque repository IDs and source-relative paths, bounded sorted unique flags, unique annotation targets, and a live resolver-issued immutable configuration. `duplicated` is computed only from collected SHA-256 digests and cannot be asserted manually.
- Treat annotations as explicit source provenance/limitations, never as instructions or capability declarations. Configuration carries no arbitrary pattern, rationale, URL, remote, path outside a selected repository, or strength override. Every annotation must resolve to a repository or file present in the supplied snapshots or the complete classification fails without partial output.
- Apply a fixed case-insensitive segment/name indicator table to collected safe relative paths. Exact vendor/third-party directory segments indicate `vendored`; generated/gen/build/dist segments and generated/minified/protobuf-style names indicate `generated`; tutorial/demo/example/sample segments indicate `tutorial`; and template/scaffold/boilerplate segments indicate `template`. These are conservative risk indicators with an explicit `path-indicator-only` limitation, not proof of ownership or source origin.
- Compute `duplicated` whenever the same collected SHA-256 digest occurs in more than one distinct selected file, within or across repositories. Preserve the duplicate count as bounded metadata but do not emit the other file paths. A digest match is exact-content duplication, not proof of copying direction or intent.
- Associate a current collected file only with bounded M2-S03 commits whose changed-path list exactly names it, then join those object IDs to the authentic M2-S04 assessments. Preserve sorted attribution states and fixed authorship limitations. If no bounded commit association exists, or no associated assessment maps to the configured target as Evidence `attributed`/`coauthored`, add `uncertain`; shallow/truncated history remains visible and also prevents an absence from being treated as provenance proof.
- Emit every required condition as a sorted `riskFlags` set drawn from `fork`, `template`, `generated`, `vendored`, `tutorial`, `duplicated`, and `uncertain`. Any flag sets support to `reduced` and Evidence strength ceiling to `weak`. A record with no detected flag has `normal` support and at most `moderate` strength, but is labeled `origin-unverified`; it is never called original or strong. Every record sets `standaloneDemonstratedDepthAllowed: false`.
- Emit only immutable `evidence-source-risk-snapshot` `0.1.0` records with repository/root IDs, head revision ID, safe source-relative reference, content digest, source category, bounded associated commit IDs, attribution states, fixed authorship/source limitations, risk flags, duplicate count, support level, strength ceiling, and the standalone-depth prohibition. Omit raw content, package values, identities, messages, URLs/remotes, absolute paths, configuration, native diagnostics, and other duplicate locations.
- Validate all three input snapshot shapes and their repository/root/object/commit relationships at the boundary. Require an authentic authorship snapshot issued for the supplied Git snapshot's subject and exact commit set. Invalid shape, mismatch, forged configuration/assessment, limit exhaustion, or dangling annotation returns one fixed non-retryable category and no partial records.

## Consequences and alternatives

The Community implementation can down-rank common source-origin hazards without network access, content execution, or pretending that path conventions prove provenance. Explicit annotations cover facts unavailable from minimized local metadata, while fixed indicators and exact digests provide reproducible automated signals. Later normalization/claim derivation receives traceable risk and authorship constraints but must still infer capabilities separately and preserve every ceiling/limitation.

Treating unflagged files as original, inferring fork status from unavailable remotes, parsing README prose, running language tools, using fuzzy similarity/embeddings, allowing arbitrary patterns, emitting duplicate peer paths, or silently ignoring unmatched annotations is rejected. Excluding all generated/vendor/tutorial/fork evidence is also rejected: reduced weak observations may remain useful as context if later Claims expose their limitations.

## Validation

Run the pinned Windows Node.js/npm path and `npm run check`. Unit tests exercise resolver boundaries, each explicit/automatic risk, digest duplication, cross-snapshot joining, authorship and history uncertainty, fixed ceilings/limitations, deterministic immutable output, malformed/forged inputs, limits, and canary-safe failures. Integration tests use only temporary synthetic repositories and the real M2 filesystem/Git/authorship chain. `FMU-E-007` asserts that fork/template/generated/vendor evidence is reduced, weak, visibly limited, and never independently permits demonstrated depth. Static inspection rejects process, filesystem, network, dynamic code, arbitrary regular-expression input, and output-bearing diagnostics in the pure modules. Review the complete diff, dependency/lockfile/public-schema stability, local links, and vulnerability result, then require protected pull-request and post-merge CI before the queue transition becomes authoritative.
