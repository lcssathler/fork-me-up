# ADR-0008: Evidence and Claim draft contracts

- Status: Accepted
- Date: 2026-09-05

## Context and task contract

M0-S08 is integrated on `main` at `ea9242f`, and the current roadmap queue marks M0-S09 as the earliest eligible slice. Local branches, worktrees, and known remote refs contain no active M0-S09 claim. The authenticated GitHub CLI is unavailable and a direct remote-ref query has no credentials, so ownership is based on the synchronized local `origin/main` evidence and is claimed by `feat/m0-s09-evidence-claim-contracts`.

Traceability: `M0-S09`, `FMU-FR-004` through `FMU-FR-006`, `FMU-FR-009`, `FMU-NFR-006`, `FMU-NFR-009`, `FMU-NFR-011`, PROTOCOL Sections 2 and 5, ARCHITECTURE Sections 5.1 through 5.3, SECURITY_PRIVACY T-04 through T-06 and T-10/T-12, and ADR-0001/0002/0007. No behavioral `FMU-E-*` evaluation applies because this slice defines unreleased authoring contracts and development validation, not claim derivation, correction precedence, repository analysis, DCP compilation, or consumer behavior.

The observable result is that `npm run schema:check` validates the existing DCP corpus plus independent Evidence and Claim `0.1.0` positive and negative fixture corpora, fails closed on malformed or unexpected fixture outcomes, and runs through the existing local/CI aggregate. In scope are the two public draft schemas, only synthetic fixtures, bounded development validators and tests, synchronized protocol/security/versioning/governance documentation, this ADR, and the M0 queue transition proposed after checks pass. No Developer Profile Store or Portable Profile Export shape, Demand Profile, provider interface, runtime package, source ingestion, persistence, MCP operation, adapter, private data, production dependency, release, publication, or remote setting is in scope.

Compatibility and migration impact are limited to unreleased drafts. Evidence and Claim begin at `0.1.0`; no released data requires migration. The DCP remains a minimized projection with an intentionally smaller inline claim summary and does not embed either independent record. Local edits, deterministic checks, temporary synthetic test data, and a reviewable local commit are allowed. Stop on a conflicting higher-authority contract, a need to weaken provenance or disclosure invariants, an unresolved high-severity finding, ownership uncertainty, or any external authorization requirement.

## Decision

- Define self-contained JSON Schema draft 2020-12 authoring contracts at `schemas/evidence/0.1.0.schema.json` and `schemas/claim/0.1.0.schema.json`, identified by stable Fork Me Up URNs. Both are closed exact-producer drafts. They are not released consumer-negotiation schemas or compatibility claims; M0-S12 still owns provider/consumer conformance and unknown-optional-field behavior.
- Evidence is an immutable `observation`, not a capability claim. It records an opaque evidence identifier; a capability signal; bounded source class, source-relative reference, opaque repository and revision references, and visibility; authorship assessment; observed and collected timestamps; categorical strength; limitations; extractor identity/version; and an explicit invalidation rule plus fingerprint.
- Source-relative references use forward-slash relative segments and reject absolute paths, drive paths, backslashes, empty segments, and `.`/`..` traversal segments. Opaque repository, revision, subject, evidence, declaration, correction, project, and claim references use the existing non-path identifier shape. Syntax does not prove authorization, redaction, identity, or source existence.
- Authorship states are `attributed`, `coauthored`, `bot`, `unknown`, and `not-applicable`. Attributed and coauthored observations require an opaque subject reference; the other states prohibit one. This represents uncertainty and shared/non-human work without turning it into a claim-strength rule. Runtime attribution policy remains M2.
- Evidence strength is `weak`, `moderate`, or `strong`; it is support metadata, not Claim confidence, observed depth, seniority, or a score. Collection must not precede observation. The checker enforces timestamp ordering without consulting the wall clock.
- Claim records retain the five protocol states and use a state-matched `basis.kind`: `evidence`, `adjacency`, `declaration`, `insufficient-evidence`, or `dispute`. This discriminates automated observation-backed support, adjacent inference, developer declaration, explicit uncertainty, and developer dispute without collapsing them into prose.
- Demonstrated and adjacent claims require evidence references; demonstrated claims also require observed depth. Adjacent claims require source capabilities and a rationale but have no observed depth for the target capability. Self-declared claims require a declaration reference and no evidence-derived depth. Insufficient-evidence claims cannot use the prohibited `does-not-know` state and have no observed depth. Disputed claims require a correction reference and preserve at least one original evidence reference; their original observed depth may remain visible.
- Claim scope is `global` or `project`; project scope requires an opaque project reference and global scope prohibits one. Every claim retains bounded limitations and freshness. These authoring constraints do not implement precedence, verify provenance resolution, or establish that referenced objects exist.
- Extend the existing bounded offline fixture machinery to all three draft contracts. Schemas are compiled locally with the already-owned Ajv `8.20.0` development dependency, no network schema loading, coercion, defaults, property removal, or arbitrary CLI paths. Diagnostics remain fixed and content-free. No dependency or lockfile change is required.
- Keep the independent Evidence and Claim records out of a DCP. The DCP schema's inline summary remains a minimized projection governed by its own disclosure and byte limits.

## Consequences and alternatives

Independent providers can review the initial provenance and claim-state boundary before runtime code exists. Exact draft constraints expose invalid authorship, scope, state/basis, traversal, timestamp, and provenance combinations early. The cost is additional draft surface that must evolve deliberately with fixtures, compatibility notes, and future generated types when a real producer or consumer package exists.

A single combined Evidence-and-Claim envelope is rejected because observations and assessments have different semantics and disclosure risks. Reusing the DCP inline claim summary as the canonical Claim is rejected because a task packet is a minimized projection. Encoding state distinctions only in free text is rejected because it is not safely testable. Numeric confidence, taxonomy registries, a correction event schema, resolver lookups, runtime precedence, and profile persistence remain deferred to their named slices.

## Validation

Run the pinned Windows Node.js/npm path and `npm run check`. Tests cover every valid claim state, evidence authorship states, exact versions and closed objects, state/basis mismatches, missing provenance, declaration and correction references, project scope, unsafe source references, timestamp validity and ordering, limits, non-mutation, bounded fixture reads, symlink/junction rejection, local-only schema references, fixed CLI diagnostics, and absence of raw source or policy-bearing fields. Manually review documentation links, fixture sensitivity, the complete diff, and contract consistency. CI for the reviewed revision must pass before integration; proposed queue transitions become authoritative only after review and integration into `main`.
