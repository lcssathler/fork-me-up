# ADR-0023: Generation-addressed atomic local profile store

- Status: Accepted
- Date: 2026-09-05

## Context and task contract

M2-S05 is integrated on protected `main` at `8e23766`, making M2-S06 the earliest eligible slice. The tree is clean, no competing worktree or local branch claims the slice, and this task is claimed by `feat/m2-s06-atomic-profile-store`.

Traceability is `M2-S06`, `FMU-FR-004`, `FMU-FR-009`, `FMU-NFR-009`, `FMU-NFR-011`, `FMU-NFR-014`, the persistence cases of `FMU-E-011`, PROJECT_SPEC Sections 10 and 14, PROTOCOL Sections 2.3/2.4 and 12, ARCHITECTURE Sections 5.4/11/12, SECURITY_PRIVACY T-06/T-10 and Sections 8/10/11, ENGINEERING Sections 3 through 8, and ADR-0009. The observable result is an implementation-internal Community store that validates serialized Store versions, activates same-directory writes atomically, detects concurrent generations, preserves the prior valid generation across failure, deterministically recovers the newest valid committed generation, and explicitly migrates a synthetic legacy Store into `0.1.0`.

In scope are a closed private store-location resolver, exact current/legacy runtime parsing, a narrow injected file port, the Node filesystem adapter, immutable generation-addressed persistence, readback verification, optimistic concurrency, bounded cleanup/recovery, one explicit forward migration, adversarial unit/integration tests, `FMU-E-011`, and synchronized documentation. Non-goals are Claim/Evidence derivation, correction behavior, import/export/delete commands, owner UI/CLI, Provider/MCP operations, repository writes, encryption, multi-user isolation, network storage, Cloud backup, public schema changes, a new dependency, release, or migration of real released data.

Allowed effects are local code/document edits, temporary synthetic store directories, deterministic tests, a short-lived branch, and the already authorized pull request/squash merge and branch deletion. Stop on public Store exposure, raw profile/path content in errors, unbounded directory/data processing, activation before validation and durable staging, overwrite of a committed generation, loss of the prior valid generation, silent concurrency conflict, a higher-authority conflict, or unresolved high-severity finding.

## Decision

- Keep the Store implementation inside `@fork-me-up/community-provider`. A resolved `0.1.0` configuration canonicalizes one existing directory and names expected opaque store and subject identifiers. Every operation uses that canonical location and rejects non-directories, canonical redirection through links, forged resolved state, unknown fields, unsafe identifiers, and content-bearing errors. Hostile replacement by the same operating-system user remains outside the early local-only isolation boundary.
- Keep the accepted implementation-internal `community-profile-store` schema at `0.1.0`. Runtime parsing is closed and bounded, validates exact envelope/internal-state fields and timestamp ordering, and reuses the Protocol's exact Portable Profile payload validation without treating the Store as an interchange contract.
- Persist committed values as immutable `community-profile-store.g-<generation>.json` files. Before activation, serialize a detached validated Store canonically, write it with exclusive creation to a same-directory nonce-bearing temporary file, sync and reread it, then create the final generation name through an exclusive hard link. The final name is never overwritten. Remove the temporary link only after activation and sync the directory where supported.
- Use generation names as the compare-and-set boundary. Creation requires no active generation and generation zero. An update supplies the observed active generation and must write the next unused generation. Concurrent writers can stage independently, but only one can create the same final generation name; the loser receives a fixed conflict and never overwrites the winner.
- On load, enumerate only a fixed bounded filename grammar, reject links/special entries, validate every bounded committed candidate, and select the highest valid generation. A malformed higher generation cannot hide a lower valid generation. The result reports `active`, `recovered`, `migrated`, or `absent`, plus counts and whether bounded cleanup remains; errors never include paths or profile content.
- Retain at least the newest and immediately preceding valid committed generations. After successful activation or recovery, best-effort cleanup may remove older recognized regular files and inactive temporaries. Cleanup failure is observable but does not relabel an already committed write as failed. Unknown directory entries are untouched.
- Define one explicit synthetic legacy `0.0.0` parser solely for migration rehearsal. It has the same profile payload but lacks `lastValidatedAt` and `migratedFromStoreSchemaVersion`. Load migrates the newest valid legacy candidate to a new `0.1.0` generation using an injected canonical validation timestamp, preserves creation/update times, records `migratedFromStoreSchemaVersion: "0.0.0"`, validates and activates it through the same atomic path, and keeps the legacy generation as rollback state. There is no claim that unreleased real user data used `0.0.0`.
- Do not use a persistent lock file. A crashed lock can block all future writes or requires unsafe lease breaking. Generation-addressed exclusive activation provides the required optimistic concurrency while a crash before activation leaves only an ignored temporary and a crash after activation leaves a complete immutable generation.

## Consequences and alternatives

Committed files are append-then-prune rather than in-place replacements, so the prior valid value survives staging, activation, readback, and cleanup failures. Recovery is deterministic and does not need a mutable pointer file. Storage remains bounded during normal operation; an abnormal directory with too many recognized candidates fails closed for explicit maintenance instead of scanning without limit.

In-place truncate/write, rename-overwrite of the only copy, an automatically broken lease lock, trusting file extensions without content validation, activating a temporary after restart, silently skipping unsupported versions, or reporting success before readback is rejected. SQLite, an external lock package, encryption, OS keychains, backup services, and owner workflows are deferred because they expand this local single-owner slice.

## Validation

Run the pinned Windows clean install and complete aggregate. Unit tests cover configuration authenticity, current/legacy version parsing, exact shape/bytes/timestamps/identifiers, deterministic migration, generation compare-and-set, exclusive activation conflict, every injected interruption point, readback mismatch, recovery ordering, malformed higher candidates, cleanup observability, immutability, and content-free failures. Integration tests use only temporary synthetic directories to prove real exclusive writes, prior-generation retention, reload, recovery, concurrent writers, orphan-temporary handling, migration, links/special entries, and bounded corruption. `FMU-E-011` verifies that success is reported only after validated readback and that a failed write leaves the prior valid generation loadable. Review the complete diff, local links, secret canaries, schema/dependency/lockfile stability, vulnerability audit, protected pull-request CI, and post-merge `main` CI.
